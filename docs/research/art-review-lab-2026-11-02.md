# Look development and controlled art review

Research date: 2026-11-02. Scope: terminology and a possible integration seam for the existing 2D Godot study. This is research and a proposal, not an implementation or an artistic approval.

## Recommended language

- **Look development (lookdev)** is the closest established umbrella for developing and evaluating an asset's visual appearance in context. More specifically, call the current activity **controlled side-by-side variant comparison**. Unity's Look Dev documentation describes comparing versions of an asset under the same light, viewing one asset under different lighting, single/multiple views, shared camera movement and environment libraries. Its example is an image-based, 3D-oriented Unity viewer; this project is applying the comparison idea to 2D, not adopting Unity or its HDRI requirements. [Unity Scriptable Render Pipeline Core 17.0.4: Look Dev](https://docs.unity3d.com/Packages/com.unity.render-pipelines.core@17.0/manual/Look-Dev.html).
- **Art Review Lab** is a proposed plain-language name for this project's future reusable capability, not a standardized industry term. A **preview scene** is the displayed environment and its lighting; a **preview profile** can name a saved scene/lighting setup. As a concrete 3D precedent, Unreal Engine 4.27 describes preview scenes and shareable profiles for meshes under different environments and lights. This supports the analogy, not a claim that its profiles are a Godot feature already built here. [Epic: Customizing the Preview Scene](https://dev.epicgames.com/documentation/en-us/unreal-engine/customizing-the-preview-scene?application_version=4.27).
- A **contact sheet** is a static grid of images for review and comparison, not the interactive process or a moving preview. Adobe describes the thumbnail-grid format. A single view, side-by-side view and exported contact sheet are complementary review outputs. [Adobe: Create contact sheets](https://helpx.adobe.com/indesign/desktop/add-graphics-and-media/add-edit-graphics/create-contact-sheets.html).
- **Asset review** is a useful general description; avoid calling this a **turntable** unless an object/camera actually rotates. The present study displays fixed 2D views.

## What already exists here

`tools/character-design-director/SKILL.md` already covers controlled concept rounds, matching view/framing/height/ground/background, source provenance, user decisions and explicit identity handoff. `tools/pixel-art-director/SKILL.md` already owns protected native editing, source and export comparisons, edit/reopen proof, animation and separations between technical proof, visual judgment and approval. `docs/workflow/art-production.md` joins these stages and requires actual Godot playback before a runtime claim. A new skill should **orchestrate a comparison session and its record**, linking to those authorities instead of duplicating their craft, approval or proof requirements.

The concrete starting point is `godot/stealth-fighter-playground-r03/`, with the findings in `docs/experiments/2026-11-02-stealth-fighter-user-variants-r01/record.md`. The current study displays Current A and user looks 01/03/04/05 in fixed REST poses at a common default 152 px displayed body height; 02 is a reference board containing the exact 03 crop. It uses repeated matching bays, common floor/scale and fixed world/camera, side-by-side/single views, look selectors, sets, guides and source-color/dim/point-light modes. The record reports native/export checks, 14 focused UI/state cases and five color/height/ground comparisons in Godot 4.7.2. These are existing project results, not new tests performed by this research. User appreciation of the review pattern and the working display height is not a final choice among the five appearances. Several looks change multiple visual properties together; only the identified 03/05 shoulder pair isolates that intended difference.

## Proposed review-session seam

These are project recommendations derived from the above precedents and existing rules, not features claimed by the cited tools:

1. Capture the question and named candidate IDs; identify originals, native sources and runtime exports/versions. Preserve an existing approved identity/baseline and prior attempts where available. If no appearance is approved, freeze the *review baseline* without describing it as user-approved art. Keep each variant separate and record exactly which properties co-vary; only attribute an isolated cause when the evidence supports it.
2. Specify what is held constant and what changes: scene/background, camera/framing, orientation, ground/anchor, display height and filtering, lighting profile and animation time. For appearance comparisons, use matched settings; for lighting comparisons, hold the asset fixed. Record actual measurements and any mismatches rather than asserting fairness from a prompt. A comparison height is not a final native resolution or gameplay decision.
3. Show actual source/reference and native/export evidence at appropriate native or integer zoom alongside the actual Godot game-sized view. Include still sheets when useful and label any resampling. Retain IDs, provenance, settings and relevant captures so feedback can be tied to the exact asset and scene.
4. Record separately: technical checks and observed engine target; agent visual observations; the user's preference, rejection or explicit approval; what remains unresolved; next named change. Do not turn a successful render, editability proof or agent recommendation into art approval.
5. Support static candidates now. For later authored animation, preserve frames, timing and anchor information and inspect real playback at the intended display size/speed; compare like phases and explicitly identify differences in timing or loop duration. Godot documents playback from individual images or sprite sheets, but the r03 study does not yet prove an animation feature. [Godot: 2D sprite animation](https://docs.godotengine.org/en/stable/tutorials/2d/2d_sprite_animation.html).
